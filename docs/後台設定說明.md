# 後台（CMS）設定說明

網站本身仍是 GitHub Pages 靜態網站；內容與帳號改由 Supabase（Auth + Postgres + RLS）管理。
後台網址：`https://zhenle2037.github.io/kuangmi-hologram/admin/`

在 `assets/config.js` 填好之前，網站一律使用內建的 `data/content.js`，外觀與功能和現在完全一樣；後台頁面則顯示「尚未連接資料庫」。

## 〇、最快的方法：一行指令（Windows PowerShell 或 Mac／Linux 終端機）

1. 到 <https://supabase.com> 用 GitHub 登入（第一次會要求建立一個 Organization，選 Free）。
2. 到 <https://supabase.com/dashboard/account/tokens> 按 **Generate new token**，名稱隨意，複製產生的 `sbp_…`。
3. 在終端機貼上並執行：
   ```bash
   bash <(curl -fsSL https://raw.githubusercontent.com/zhenle2037/kuangmi-hologram/main/tools/setup_supabase.sh)
   ```
   **Windows** 請開「PowerShell」（開始選單搜尋 PowerShell），貼上：
   ```powershell
   irm https://raw.githubusercontent.com/zhenle2037/kuangmi-hologram/main/tools/setup_supabase.ps1 | iex
   ```
   依提示貼上 Token、輸入你的 Email。腳本會自動完成下面第 1、2、3、5 步與第 4 步的 Email 登入與網址設定，最後印出 `supabaseUrl` 與 `supabaseAnonKey`。
4. 把印出的兩行貼給 Claude（或自行填入 `assets/config.js`）。用完可回到 Token 頁面把 Token 刪除。

以下是手動做法，與腳本做的事相同。

## 一、需要由帳號擁有者親自完成的步驟（約 15 分鐘）

以下步驟需要登入你自己的 Supabase／Google 帳號，無法由程式代為完成。

### 1. 建立 Supabase 專案
1. 到 <https://supabase.com> 用 GitHub 或 Email 註冊並登入（免費方案即可）。
2. **New project** → 名稱自訂（例：`kuangmi`）→ 設一組資料庫密碼（自行保存，不要放進 GitHub）→ Region 建議選 `Northeast Asia (Tokyo)` 或 `Southeast Asia (Singapore)`。

### 2. 建立資料表、權限與初始資料
專案建好後，到左側 **SQL Editor** → **New query**，依序把下列三個檔案的全部內容各貼上一次並按 **Run**：

1. `supabase/migrations/20261015000100_schema.sql`（資料表）
2. `supabase/migrations/20261015000200_security.sql`（RLS、角色、函式）
3. `supabase/migrations/20261015000300_seed.sql`（把現有 76 個名相、108 珠位、17 章等資料匯入，並建立第一個正式版本）

（若你熟悉 Supabase CLI，也可在專案資料夾執行 `supabase link` 後 `supabase db push`。）

### 3. 指定網站擁有者（Owner）
在 SQL Editor 執行（把 Email 換成你登入後台要用的 Email）：

```sql
select public.bootstrap_owner('你的Email');
```

這個函式只能在 SQL Editor（資料庫管理者）執行，網頁上的任何人都無法呼叫。之後新增 Editor 或其他 Owner 都在後台「成員權限」頁操作即可。

### 4. 開啟登入方式
左側 **Authentication** →

- **Sign In / Providers → Email**：保持啟用（用 Email 收登入連結，不需密碼）。
- **Sign In / Providers → Google**（可選，想用 Google 帳號登入時）：
  1. 到 Google Cloud Console → APIs & Services → Credentials → **Create credentials → OAuth client ID** → 類型選 **Web application**。
  2. **Authorized redirect URIs** 填入 Supabase Google 設定頁上顯示的 Callback URL（形如 `https://<你的專案>.supabase.co/auth/v1/callback`）。
  3. 把 Google 給的 Client ID 與 Client Secret 貼回 Supabase 的 Google 設定並儲存。Client Secret 只存在 Supabase，不放進 GitHub。
- **URL Configuration**：
  - Site URL：`https://zhenle2037.github.io/kuangmi-hologram/`
  - Redirect URLs 加入：`https://zhenle2037.github.io/kuangmi-hologram/admin/` 與 `https://zhenle2037.github.io/kuangmi-hologram/`

### 5. 把公開設定填進網站
左側 **Project Settings → API**（或 Data API），複製：

- **Project URL**
- **anon public** key（或新版的 **Publishable key**）

填入 `assets/config.js`：

```js
window.KM_CONFIG = {
  supabaseUrl: "https://xxxx.supabase.co",
  supabaseAnonKey: "貼上 anon public key",
  supabaseJs: "https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.117.2/dist/umd/supabase.js"
};
```

提交並推送後，GitHub Pages 約一分鐘更新。也可以把這兩個值貼給 Claude，由 Claude 代為修改並推送。

> anon／publishable key 本來就設計成放在前端，所有權限由資料庫 RLS 與函式檢查。
> **絕對不要**把 `service_role` / secret key、資料庫密碼、Google Client Secret 放進 `assets/config.js` 或任何提交到 GitHub 的檔案。

### 6. 第一次登入
打開 `/admin/`，用第 3 步的 Email（Email 連結或 Google）登入，應看到「Owner 擁有者」與全部分頁。

## 二、環境變數／設定值清單

| 名稱 | 放在哪裡 | 是否機密 | 用途 |
|---|---|---|---|
| `supabaseUrl`（Project URL） | `assets/config.js` | 否（公開） | 網站與後台連線 |
| `supabaseAnonKey`（anon / publishable key） | `assets/config.js` | 否（公開，權限受 RLS 限制） | 網站讀正式版本、後台登入後呼叫函式 |
| `supabaseJs` | `assets/config.js` | 否 | supabase-js 程式庫網址（固定版本） |
| 資料庫密碼 | 只在你自己保管／密碼管理器 | **是** | `supabase db push` 等 CLI 操作 |
| `service_role` / secret key | 只在 Supabase 後台 | **是** | 本專案**不需要**，不要使用或提交 |
| Google OAuth Client ID / Secret | 只在 Supabase → Auth → Google | Secret **是** | Google 登入 |
| `SUPABASE_ACCESS_TOKEN`（可選） | 只在本機環境變數 | **是** | 使用 Supabase CLI 時 |

`.gitignore` 已排除 `.env*` 與 `supabase/.temp/`，避免誤傳。

## 三、角色與權限（由資料庫強制）

| 動作 | 訪客 | Editor | Owner |
|---|---|---|---|
| 瀏覽公開網站（只讀最新正式版本） | ✔ | ✔ | ✔ |
| 讀取草稿、預覽（`?preview=1`） | ✘ | ✔ | ✔ |
| 編輯名相、珠位、章節對應、章／節內文（存為草稿） | ✘ | ✔ | ✔ |
| 封存名相 | ✘ | ✔ | ✔ |
| 永久刪除名相、刪除節 | ✘ | ✘ | ✔ |
| 修改分類、網站標題、導師引文、部件譬喻 | ✘ | ✘ | ✔ |
| 正式發布、還原歷史版本 | ✘ | ✘ | ✔ |
| 授權／撤銷成員 | ✘ | ✘ | ✔ |
| 檢視操作紀錄 | ✘ | ✔ | ✔ |

訪客無法讀取任何資料表，只能讀 `content_revisions` 中 `kind = 'publish'` 的版本。所有寫入都經過 `security definer` 函式，函式內先檢查角色；資料表本身不開放直接寫入。

### 固定規則（資料庫層檢查）
- 108 顆珠位固定，不能新增或刪除；4 顆隔珠（27、54、81、108）不能放名相。
- 一個名相只有一個主珠位；一顆珠只放一個名相；名相只能放在主分類那一區。
- 跨類顯示（例：持咒主分類「修」、顯示於「修、行」；中有解脫主分類「果」、顯示於「果、修」）只增加顯示分類，不增加珠位。
- 發布前檢查：108 珠位與 4 隔珠完整、名相珠位與主分類一致、顯示分類包含主分類；有問題時「正式發布」停用並列出原因（名稱空白則在儲存時即被拒）。

### 草稿、發布與還原
- 後台的每次儲存都只改「草稿」；訪客看到的是最近一次「正式發布」的快照。
- 每次發布會保存完整快照，可在「發布與版本」與目前草稿比較差異、還原。
- 還原會先把目前草稿自動備份成一個版本，再載入指定版本到草稿；需再按「正式發布」才會公開。
- 同一項目兩人同時編輯時，後存的一方會收到「版本衝突」，可選擇放棄自己的修改或確認後覆蓋。
